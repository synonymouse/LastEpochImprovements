# Review — Unity 6000.4 compatibility changes

Baseline: `68958ef5ec537955890afe6d021fe8e90099fd1c` (working-tree changes).
Scope: mod sources/project, five compatibility/repair tools and diagnostics.
Two independent reviews examined documented standards and the requirements
recorded in the troubleshooting conversation. Existing local agent instructions
and OpenCode model-routing research were context rather than authored changes.

## Standards

No hard violations of the documented repository standards were found.
The standards reviewer identified four correctness/maintainability findings:
stale repair staging files, shrine-request cancellation races, incomplete
Bazaar searches, and deduplication limited to pending rare markers.
All four were corrected. Shared repair-code indentation was normalized.

## Spec

Five P2 behavior gaps were identified: interrupted repair recovery, late/inactive
rare visuals, duplicate/corpse rare markers, consumed/replaced shrine ownership,
and affix-modal failure allowing an unfiltered search. These were corrected:

- Repair uses exclusive, unique staging files and cleans them on failure.
- Rare waits continue for a living actor instead of expiring after 15 seconds.
- One live marker is retained per actor; the processor follows replacement
  visuals and removes the marker on actor death/destruction.
- Shrine state is owned by `ShrineSync`; generation IDs protect cancellation,
  target replacement is handled, and confirmed client use marks it consumed.
- Affix setup reports success; a timeout or missing requested entry aborts
  automated submission.

Follow-up review identified global scene-load cleanup as unsafe for additive
scenes. It was replaced with periodic pruning of destroyed/dead owners only.
The final targeted re-review reported no remaining concrete lifecycle defects.

## Verification

- Release and Special builds: no errors or warnings; `DeployToGame=false`
  prevents verification builds from replacing the installed DLL.
- All five tool projects build successfully.
- Real corrupted-CoreModule replay: stale legacy staging file does not block
  repair; repaired DLL loads; repeated repair leaves bytes unchanged.
- Locked-target test: failed replacement preserves original bytes and removes
  its staging file.
- Earlier in-game confirmation: Explorer F7, shrine effects/distant markers,
  rare markers and absence of Stage: 3 all passed before the review.
- Review-only lifecycle changes are build/static-review verified; full gameplay
  validation of these additional edge cases remains separate.
